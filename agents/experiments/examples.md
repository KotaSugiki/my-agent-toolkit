# 分野の異なる利用例

以下は、このツールキットの手順を確認するために作成した架空の例です。目的・制約・数値・人間の回答はすべて説明用です。実際の実験結果やエージェントの実行記録ではありません。

各例は別の導入先を想定します。パスはそれぞれの導入先からの相対パスです。記録する全項目は [記録形式](../../skills/setup-experiments/references/records.md)に従います。

## 例1：既存の文書検索プロジェクト

### セットアップ

既存のコード・設定・文書から、質問と正解文書を含む `data/search-v1.jsonl`、実行コマンド `python search.py --config <設定>`、評価コマンド `python evaluate.py --results <結果>` を確認したとします。スキルは調査結果、目的・範囲、保存先を提示し、今回の前提として使ってよいか質問して回答を待ちます。その後、未確認の費用上限を質問します。調査済みのデータやコマンドの再入力は求めません。

`docs/experiment-project.md` の `project-v1` には、「必要な文書を見つける品質を保ち、不要な文書の確認を減らす」という目的を保存します。変更可能な条件は検索のしきい値、固定条件はデータの版と分割、評価スクリプトです。上限は1実験につき比較条件3種類、合計15回の実行、30分、外部APIの利用なしとします。設定・結果・ログは `artifacts/experiments/<実験ID>/` に保存します。フィードバックは人間の回答を親が実験記録へ追記します。

セットアップは、新たな検出率や目標値を定めません。目的・範囲・制約について、人間の確認済みと記録します。

### 最初の計画と実行

`experiment-planner` は、「しきい値を上げれば、必要な文書の見落としを増やさず不要な候補を減らせる」という仮説を立てます。評価指標は正解文書の検出率、候補の適合率、1質問あたりの候補数とします。検出率は正解文書全件を分母、適合率は提示候補全件を分母と定義します。

`docs/experiment-targets.md` の `targets-v1` に、検出率99%以上かつ候補数が比較対象以下という目標を保存します。99%は、この例で人間が示した品質要求に由来すると記します。比較対象はしきい値0.4、変更条件は0.5と0.6、同じ質問集合で各5回測定し、乱数を使わない実装であることを確認します。目標値・指標・判定基準は提案として提示し、人間の回答後に確認者・日時・確認内容を記録します。

`docs/experiments/exp-20261006-001.md` の計画へ、前提・目標値の版と内容の写し、確認記録への参照を保存します。実行準備が揃った後、実行担当は15回の実行番号、設定、コマンド、コードの状態、環境、開始・終了日時、終了コード、結果とログを残します。

### 評価とレポート

架空の観測値として、0.4では検出率99.5%・候補数10件/質問、0.5では99.2%・8件/質問、0.6では98.0%・6件/質問だったとします。評価担当は反復ごとの値と集計範囲を確認し、0.5は目標達成、0.6は候補数が減っても検出率の目標未達と記します。適合率や反復の詳細が欠けていれば、その指標の評価は判断不能として残します。

レポート担当は `docs/experiments/20261006-exp-20261006-001-report.html` を保存します。冒頭には「0.5は目標達成、0.6は品質の目標未達」という結論と、0.5の周辺を調べるかという判断事項を短く示します。検出率のグラフには99%の目標値と全条件を表示し、指標を切り替えると候補数を比較できます。品質が下がった0.6も掲載します。未確認の適合率と一般化の限界を要約に示し、詳しい反復結果や根拠は折りたたみとリンクで確認できます。実験記録には要約とHTMLへのリンクだけを残します。

### フィードバック後の次の実験

人間が「0.5の周辺を調べたい」と回答したとします。親は実際の回答・日時を最初の実験記録へ追記し、次の実験 `exp-20261006-002` を計画担当へ依頼します。

次の計画では `project-v1` と `targets-v1` を引き継ぎ、しきい値0.45・0.5・0.55を比較します。前の実験IDと回答の所在、条件への反映内容を記録します。しきい値だけの変更なのでセットアップと目標値の再確認は行いません。前の実験の失敗した条件を消したり、検出率99%の目標を98%へ下げたりしません。

## 例2：新規の数値計算プロジェクト

### 未準備のセットアップ

コードも入力データもない状態で、「計算精度を保ちながら積分計算を速くしたい」と依頼されたとします。スキルは新規プロジェクトとして整理し、対象とする関数、参照値、実行環境、比較する計算方法、誤差の測り方を人間に確認します。

最初の質問に回答がない間は、`docs/experiment-project.md` を作りません。目的・範囲と保存先への回答後は、確認した内容を「対話中」の草案として保存します。目的と、データ・実行手順・評価方法が未準備であること、必要な準備作業を対話で確認して追記します。全項目の確認が揃えば `project-v1` を「確認済み」としますが、実行準備は未完了です。この時点では数値の目標を推測せず、実験実行へ進めません。

### 準備後の計画

人間が対象関数と参照値を指定し、導入先で入力と `integrate.py`、誤差と時間を測る `measure.py` が用意されたとします。前提を `project-v2` として更新し、目的は保持します。固定条件は関数集合・入力範囲・機器・Pythonの版、変更条件は分割数と計算方法です。上限は各条件5回、合計15回、10分、外部サービスなしとします。

計画担当は「計算方法を変えれば、誤差を増やさず計算時間を減らせる」と仮説を立てます。`targets-v1` に最大絶対誤差0.000001以下と、5回の実行時間の中央値が比較対象の90%以下という目標を提案します。前者は人間の精度要求、後者はこの例の時間短縮要求が根拠です。測定の単位・集計対象、比較対象、誤差と時間を同時に満たす判定基準を、人間の回答後に確認済みとして保存します。

`exp-20261006-001` の計画では `project-v2` と `targets-v1` の写し、入力・コード・環境、実行と評価コマンド、保存先を記します。設定・結果・ログは `artifacts/experiments/exp-20261006-001/` に保存します。

### 失敗と改善なしの扱い

比較対象は5回すべて成功し、方法Aは1回失敗、方法Bは5回成功して時間が比較対象の105%だったとします。実行担当は方法Aの失敗ログと終了コードを保持します。再試行する場合は上限を確認し、元の失敗を残して別の実行番号を付けます。

評価担当は、方法Aの欠測をゼロ秒として補いません。計画した5回の比較が揃わないため、方法Aの時間に関する判定を判断不能とします。方法Bは精度を満たしていても時間の目標未達・改善なしと記します。

レポート担当は、方法Aの判断不能と方法Bの目標未達をHTMLの冒頭に示します。方法Bは比較対象を100%として105%、目標値90%をグラフで比較します。方法Aは欠測として示し、失敗ログと不足の理由は折りたたみから確認できます。親は短い要約とHTMLへのリンクを提示し、「失敗条件を調べるか、別の計算方法を試すか、終了するか」を人間に尋ねます。回答がなければ回答待ちのまま終了し、次の実験を自動的に始めません。

## 追加FBの利用確認

以下は導入先で実際のエージェントに確認する項目です。架空の例への当てはめと、実際の利用テストの結果を区別して記録します。

| 場面 | 確認する動作 |
| --- | --- |
| スキルの導入・使い方の質問だけ | 前提文書を作成・更新しません。 |
| セットアップを依頼し、最初の質問に未回答 | 調査結果と確認質問を提示し、前提文書を保存せず待ちます。既存情報が揃っている場合も確認します。 |
| 目的・範囲と保存先に回答し、残る質問に未回答 | 確認した内容だけを草案へ反映し、状態は「対話中」です。全項目の確認後も、未準備の環境を実行可能とは扱いません。 |
| 保存先や目標値が未確定の計画 | 確認待ちの計画を一時的な `.md` ファイルに保存し、その場所を示します。 |
| 成功・失敗・欠測が混在する結果 | HTMLの短い要約に未達・判断不能も示し、元データとグラフを照合します。折りたたみ・切り替えをブラウザで操作して確認します。 |
| HTMLスキルが未導入 | 別スキルを導入せず、HTMLと視覚表示・詳細を確認できる操作を作成し、未利用を報告します。 |

## 手順の確認結果

文書検索と数値計算のどちらも、同じ4担当と記録形式で、分野固有のデータ・実行・評価方法を導入先から与えられます。前提がない場合は不足を保存し、条件だけの変更では前提と目標値を引き継ぎます。失敗・改善なし・未回答も記録できる構成です。

これは手順と記録形式への当てはめによる確認です。実際のモデルを使った担当の判断品質や、各分野の実験処理の動作を保証するものではありません。
