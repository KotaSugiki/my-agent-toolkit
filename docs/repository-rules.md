# リポジトリの取り扱いルール

このリポジトリでは、変更の目的が履歴から分かり、ツールが増えても配置に迷わない運用を目指します。人による作業とAIエージェントによる作業に、同じルールを適用します。

## コミットメッセージ

コミットメッセージの先頭行は、次の形式にします。

```text
<type>(<scope>): <変更内容>
```

`type` は変更の種類を表すプレフィックスです。`scope` は対象を表し、`skills`、`hooks`、`repo` などを指定します。対象が明確なら、括弧ごと省略できます。変更内容は日本語で、何を変えたかが分かる短い1行にします。

| プレフィックス | 用途 |
| --- | --- |
| `feat` | ツール、スキル、プロンプトなどの新規追加や機能追加 |
| `fix` | 不具合や誤った動作の修正 |
| `docs` | README、利用方法、設計方針などの文書の追加・更新 |
| `refactor` | 動作を変えずにコードや構成を整理する変更 |
| `perf` | 実行速度や資源使用量の改善 |
| `test` | テストの追加・修正 |
| `style` | 動作を変えない空白、整形などの変更 |
| `build` | 依存関係やビルド方法の変更 |
| `ci` | 自動テストなど、継続的インテグレーションの設定変更 |
| `chore` | 上記に当てはまらない保守作業 |
| `revert` | 過去のコミットの取り消し |

スキルやプロンプト自体の指示を追加・修正する場合は、文章であっても機能として扱い、`feat` または `fix` を使います。

```text
feat(skills): 日本語記述のスキルを追加する
fix(hooks): 実行前処理のパス判定を修正する
docs(repo): リポジトリの取り扱いルールを定める
chore(repo): 初期ディレクトリ構成を作成する
```

1コミットには、1つの目的に関係する変更をまとめます。本文は、理由や影響を補足する必要がある場合に記載します。既存の使い方が通用しなくなる変更は、`feat(hooks)!:` のように `:` の前に `!` を付け、本文の `BREAKING CHANGE:` に影響と移行方法を書きます。

## ブランチの命名

作業ブランチは `main` から作成し、次の形式で命名します。

```text
<type>/<short-description>
```

`type` はコミットメッセージと同じプレフィックスを使います。説明部分は英小文字・数字・ハイフンで記述し、変更の目的が分かる名前にします。

```text
feat/add-ja-text-communication
fix/hook-path-resolution
docs/repository-rules
```

1ブランチでは1つの目的を扱います。変更を取り込んだ作業ブランチは削除します。常設ブランチは `main` のみとし、必要になるまでは `develop` やリリース専用ブランチを設けません。

## mainブランチ保護

`main` は取り込み済みの変更を管理するブランチとします。履歴の上書きにつながる強制pushと、`main` 自体の削除は禁止します。このルールはリポジトリ所有者とAIエージェントにも適用します。

ドキュメントを含むすべての変更は、作業ブランチからプルリクエストを作成し、`main` に取り込みます。`main` への直接pushは許可しません。誤字修正などの小さな変更にも、同じ手順を適用します。

プルリクエストは、差分を確認してから変更を取り込むための手順です。GitHubの公式ガイドでも、ドキュメントにGitHub flowを使っていると説明しています。[GitHub flow（公開日不明、2026/10確認）, Introduction](https://docs.github.com/en/get-started/using-github/github-flow#introduction)

個人運用のため、他者による承認は必須にしません。取り込む前に作成者が差分を確認し、変更に応じた動作確認を行います。プルリクエストのタイトルはコミットメッセージと同じ形式にします。取り込み時は、作業中のコミットを1つにまとめる方法（Squash and merge）を基本とします。

GitHub側の保護設定は、次の方針とします。

| 設定対象 | 方針 |
| --- | --- |
| 対象ブランチ | `main` |
| 強制push・ブランチ削除 | 許可しません |
| 管理者による保護の迂回 | 許可しません |
| プルリクエスト必須 | ドキュメントを含むすべての変更で必須にします |
| 承認レビュー・必須の自動チェック | 現時点では必須にしません。自動チェックの導入時に見直します |

GitHubのブランチ保護は、対象ブランチへのpushやプルリクエストに要件を設定する仕組みです。[GitHub Docs（公開日不明、2026/10確認）, About branch protection rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#about-branch-protection-rules)

本リポジトリでは、上記の設定方針と、すべての変更をプルリクエスト経由で取り込む手順を併用します。この文書は方針を定めるものであり、GitHub側の保護設定の適用状況は別途確認します。

## Issue起票とPR作成

Issueには課題や検討事項を記録し、PRには変更内容と確認結果を記載します。GitHub・Giteaで操作する際の作成先の確認、認証、操作方法については、[GitHub・GiteaでのIssue起票とPR作成](github-gitea.md)を参照してください。

## 編集元と導入先

ツール、スキル、プロンプトなどの編集元は、このリポジトリとします。

導入先で修正した内容は、原則として編集元には反映しません。導入先の変更を同期したり、編集元へ戻したりすることは必須にしません。

導入先の変更のうち、リポジトリ所有者が個人的に良いと思ったものだけを選んで採用します。採用する場合は、このリポジトリで変更を行い、通常のプルリクエストの手順で取り込みます。AIエージェントは、導入先に変更があることだけを理由に、編集元へ反映しません。

### 種類ごとの導入方法

このリポジトリでは、対象の種類に応じて次の導入方法を採用します。

| 対象 | 導入方法と説明の記載先 |
| --- | --- |
| `skills/` | `npx skills` を使います。共通の手順は [Skillsの導入方法](skills-installation.md)、各スキルの使い方は付属の `README.md` に記載します |
| `harnesses/` | 各ハーネスの `README.md` に、必要な依存関係の導入、セットアップ、実行方法を記載します |
| `hooks/` | 各フックの利用説明に、対応エージェント、ファイルの配置先、イベントへの登録・解除方法を記載します |
| その他のツール・素材 | 追加時に、各ツール・素材の利用説明へ導入方法を記載します |

`npx skills` を使う方針は、Skillsの導入に適用します。独立したハーネスやフックは、上記の個別の手順で導入します。現時点で中身がないディレクトリは、実際のツールを追加する際に手順を定めます。

## 配置単位と命名

単体で完結するツールは、用途に合うディレクトリに1ファイルとして配置します。複数ファイルで構成するツールは、`<分類>/<名前>/` にまとめます。Skillsは `skills/<名前>/SKILL.md` を基本とし、利用説明や補助ファイルも同じディレクトリに置きます。

独自に付けるファイル名とディレクトリ名は、英小文字・数字・ハイフンを基本とします。`README.md`、`SKILL.md`、`LICENSE` などの所定の名前と、外部ツールが要求する名前は、その形式に従います。

## 最低限の利用説明

各ツールには、目的・前提条件・使い方を記載します。単体ファイルは冒頭の説明やコメント、複数ファイルのツールは付属の `README.md` を基本とします。スキルの利用者向け説明は、エージェント向けの指示である `SKILL.md` と分け、付属の `README.md` に記載します。

導入にパッケージマネージャを使う場合は、その前提条件、導入コマンド、導入先、確認方法、更新・削除の方法を説明します。共通の手順は1か所にまとめ、各ツールからリンクで参照します。

## 外部由来の素材の記録

外部から取り込むスキル、プロンプト、コードなどには、次の情報を記録します。

- 取得元URL。ローカルから取得した場合は取得元の場所も記載します。
- 取得日と、分かる場合はバージョン、タグ、コミットなどの取得時点を特定する情報。
- 元のライセンス情報と、元から付属するライセンスや著作権表記。
- 独自変更の有無と、変更した場合はその概要。

複数ファイルの素材は、同じディレクトリの `provenance.md` に記録します。単体ファイルは冒頭の説明やコメントに記録し、コメントを記載できない形式では付属文書にまとめます。確認できない情報は推測で補わず、「未確認」と記載します。元から付属するライセンスや著作権表記は保存します。

## ドキュメントの階層

利用方法や設計方針は `docs/` に配置します。ディレクトリの深さは、リポジトリルートから数えて2階層までとします。`docs/` が1階層目、`docs/<分類>/` が2階層目です。

```text
docs/repository-rules.md        # 可
docs/hooks/usage.md             # 可
docs/hooks/codex/usage.md       # 不可：ディレクトリが3階層
```

最初は `docs/` 直下に置き、関連する文書が増えてから分類用のディレクトリを作ります。文書名と分類名には英小文字・数字・ハイフンを使います。

ルートの `README.md` と、エージェントが読む `AGENTS.md` などの所定の入口ファイルは、`docs/` の外に置きます。スキル本体の `skills/<名前>/SKILL.md`、テンプレートや使用例に含まれる文書も、それぞれの対象と一緒に配置します。外部ツールが要求するファイル名や構成は、その仕様に従います。

同じルールの本文は1か所に置き、他の文書からはリンクで参照します。空ディレクトリの `.gitkeep` は、実際のファイルを追加した時点で削除します。
