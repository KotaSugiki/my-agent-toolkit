オンラインショップで注文が確定するまでの仕組み

backend onboarding / order confirmation

注文確定は、ボタンが押された時点ではなく、在庫の確保・支払いの承認・注文の記録がそろった時点で成立します。この文書は、その判断を担う部品と流れを、バックエンド開発の新人向けに順を追って説明します。

  6. 補足と限界
  • 確定の条件は3つ。在庫引当、与信の承認、注文DBへの記録
  • 支払いは外部の決済ゲートウェイに依存するため、失敗と再試行を設計に含める
  • 再試行は回数と待ち時間に上限を置き、同じ注文を二重に請求しない

背景と要点

オンラインショップの「注文する」ボタンの裏では、複数のシステムが順番に呼ばれます。どれか1つが欠けたまま確定すると、在庫がないのに売れてしまう、あるいは請求だけが残るといった事故になります。そのため、確定は次の3つがそろったときだけにします。

  • 在庫引当(注文分の在庫を、ほかの注文に売れないよう確保すること)ができた
  • 与信(カード会社に支払い能力を問い合わせ、金額分の枠を押さえること。オーソリとも呼ぶ)が承認された
  • 注文の内容を注文DBに記録できた

注文確定にかかわる部品

中心になるのは注文APIです。Webアプリからリクエストを受け取り、在庫サービスと決済ゲートウェイ(カード会社や銀行との通信を代行する外部サービス)を呼び、結果を注文DBへ保存します。確定した後のメール送信や出荷準備は、メッセージキュー(処理の依頼を一時的にためておき、受け手が自分のペースで取り出せるようにする仕組み)へ通知を出すだけにして、注文APIの応答時間に含めません。

確定の判断ロジック

注文APIは、確定の可否を次の順で判断します。まず在庫が足りるかを確かめ、足りなければその場で失敗にします。次に決済ゲートウェイへ与信を依頼し、承認されれば注文を確定します。承認されなかったときは、再試行の上限に達していなければ、待ってから与信をやり直します。上限に達したら失敗にします。

失敗には種類があります。在庫不足は何度やっても結果が変わらないため、再試行しません。決済の一時的なエラー(通信の途切れやタイムアウト)は、待てば成功する見込みがあるため再試行の対象にします。カード会社が明確に拒否した場合も再試行せず、失敗にします。ただし図2では、この区別は「再試行できるか」の判断に含めています。

再試行にかかる時間

再試行は成功の確率を上げますが、そのぶん待ち時間が増えます。1回の与信が承認される確率を $p$、最大の試行回数を $n$ とすると、試行回数の期待値 $\mathtt{E}[N]$ は次の式で表せます。$k$ 回目までの試行がすべて失敗する確率 $(1-p)^k$ を足し合わせたものです。

$$ \mathtt{E}[N] = \sum_{k=0}^{n-1} (1-p)^k = \frac{1-(1-p)^n}{p} $$

たとえば $p = 0.9$、$n = 3$ なら $\mathtt{E}[N] \approx 1.11$ で、多くの注文は1回で済みます。期待される所要時間は、これに1回あたりの時間と待ち時間を掛けて見積もります。

再送のたびに別の請求が立つと困るため、同じ注文には同じ識別子を渡します。これで冪等性(同じリクエストを何度送っても、結果が1回分と同じになる性質)を保てます。次のコードは、待ち時間を倍々に増やす(指数バックオフ)再試行の例です。 

import time

def confirm_order(order, max_tries=3, base_wait=0.2):
    if not inventory.reserve(order.items):
        return "failed: out_of_stock"

    for attempt in range(max_tries):
        # 同じ order.id を渡すので、再送しても二重請求にならない
        result = gateway.authorize(order.total, idempotency_key=order.id)
        if result.approved:
            db.save(order, status="confirmed")
            queue.publish("order.confirmed", order.id)
            return "confirmed"
        time.sleep(base_wait * 2 ** attempt)  # 0.2秒、0.4秒、0.8秒

    inventory.release(order.items)
    return "failed: payment_declined"

部品ごとの遅延の例

再試行の待ち時間を決めるには、各部品の遅さを知る必要があります。下の図は、5つの部品についてp95(計測値を小さい順に並べたときの95%目の値。遅い側の目安になる)を並べたものです。数値は説明のための仮の値で、実測ではありません。

決済ゲートウェイだけが桁違いに遅いため、再試行の待ち時間とタイムアウトは、この部品に合わせて決めます。 在庫サービスや注文DBの遅延は、確定までの合計時間にほとんど効きません。

補足と限界

この文書は、仕組みの骨格をつかむために単純化しています。実際のシステムとの主な違いは次のとおりです。

事象この文書での扱い
在庫不足即座に失敗にする
決済の一時的エラー上限まで再試行する
カード会社の拒否再試行せず失敗にする
  • 確保した在庫は、与信が失敗したあとで解放する必要があります。解放の失敗や、確定後の取り消しは扱っていません
  • 注文APIの途中で障害が起きたときの整合性の取り方(補償処理など)は扱っていません
  • 図3の数値は仮の値です。実際の値は自分たちの計測で確かめてください
