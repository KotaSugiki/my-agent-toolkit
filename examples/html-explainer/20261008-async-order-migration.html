注文確定を非同期へ移行する

backend onboarding / async order confirmation

背景と要点

いまの注文確定は、注文APIが在庫サービス、決済ゲートウェイ、通知サービス、出荷サービスを同期で順に呼び、全部の結果がそろってから応答します。同期呼び出しは、相手の処理が終わるまで待ってから次へ進む呼び方です。呼び出しが1つ遅くなるだけで、待ち時間がそのまま応答時間に積み上がります。

そこで、注文を確定するために結果が必要な処理だけを同期のまま残し、それ以外を非同期に移します。非同期処理は、結果を待たずに依頼だけを出し、相手が自分のペースで処理する方式です。依頼の受け渡しにはメッセージキューを使います。この文書では、構成の前後、処理の流れ、負荷試験の結果の例、移す順序、進め方の順に見ていきます。

構成の変化

移行前は、注文APIが在庫サービス、決済ゲートウェイ、通知サービス、出荷サービスを同期で順に呼びます。どれか1つが遅いと待ち時間が積み上がり、Webアプリへの応答も遅れます。注文APIは最後に注文DBへ保存して応答します。

移行後は、注文APIが同期で呼ぶ相手を在庫サービスと決済ゲートウェイの2つだけにします。注文DBへ保存した後、注文が確定したという知らせ(イベント)order.confirmed をメッセージキューへ発行して応答します。メッセージキューは、受け取った知らせを一時的に預かり、購読者へ順に配る仕組みです。出荷サービスと通知サービスはこのキューを購読し、注文APIの応答を待たせずに非同期で処理します。

図1では、出荷と通知を起動する線の起点が、注文APIからメッセージキューへ付け替わっています。中央の変更台帳は、変わった点を1件ずつ書き出したものです。Webアプリへ返す応答の矢印は、行きの接続と対なので描いていません。この図は構造の前後だけを示し、切り替えの手順や失敗時の再送は含みません。

注文確定の流れ

Webアプリから POST /orders を受けた注文APIは、外部サービスである決済ゲートウェイを呼び、承認を待ってから注文を注文DBに保存します。そのうえで、確定を知らせる order.confirmed イベントをメッセージキューへ発行し、Webアプリへ 201 Created(作成に成功したことを示すHTTPステータス)を返します。Webアプリが待つのは、ここまでです。在庫サービスの呼び出しもこの区間に含まれますが、図2では省いています。

出荷サービスは、キューを購読して(届くイベントを受け取る登録をして)います。イベントの配信は応答の後に行われるため、出荷の処理が遅れても失敗しても、注文の応答時間には影響しません。通知サービスも出荷サービスと同じ形でキューを購読するので、図2から省いています。図の実線は応答を待つ同期の呼び出し、破線は戻りと、応答を待たない非同期の送信です。

同じ流れを、担当するサービスの側から見たのが図3です。横方向が処理の順、縦方向が担当するサービスで、ステップ1〜4が同期、5〜6が非同期です。太枠の「注文確定」が、同期と非同期の境目です。実線の矢印は同期の引き継ぎ、破線の矢印はキュー経由の非同期の受け渡しを表します。矢印は処理の順序を表すので、在庫サービスと決済ゲートウェイを実際に呼ぶのは、どちらも注文APIです。

応答時間の比較

非同期にすると注文APIの応答時間がどう変わるかを、負荷試験で確かめます。負荷試験とは、本番に近い量のリクエストを人工的に流し、処理の速さや失敗の割合が基準を満たすかを確かめるテストです。図4は、同時リクエスト数を100から1600まで2倍ずつ増やしたときの、注文APIの p95 応答時間です。p95 応答時間とは、全リクエストを応答の速い順に並べたとき、下から95%目のリクエストが要した時間で、遅い側の利用者が体感する待ち時間の目安になります。

同期方式(灰色の線)は、同時リクエスト数が増えるほど急に悪化し、100件の120msから1600件の1500msまで約12倍になります。出荷や通知の処理時間が、注文APIの応答に積み上がるためです。非同期方式(赤の線)は、出荷と通知をキューへ預けて待たないので、95msから230msまでの増加にとどまります。横軸は2倍ずつの等間隔なので、線の傾きは「負荷が倍になるごとの増え方」を表します。

キューの滞留と通知の遅れ

非同期にすると、通知メールは注文の応答と切り離され、キューに溜まった順に送られます。キューに処理待ちのまま残っているメッセージの数を、滞留数と呼びます。図5は、滞留数(横軸、件)と、通知メールが送られるまでの遅延(縦軸、秒)を、22回の計測を1点ずつ表した散布図です。

点は右上がりに並び、滞留数が多いほど遅延が長くなる傾向が読めます。破線は最小二乗法で引いた傾向線です。ただし点は線の周りにばらつくので、滞留数だけで遅延が決まるわけではありません。運用では、滞留数に上限を決めて監視し、超えたら通知サービスのコンシューマ(キューからメッセージを取り出して処理する側)を増やすなどの対応を取ります。

最初に移す処理

すべての処理を一度に非同期へ移すと、手間も失敗したときの影響も大きくなります。そこで、移行の候補を「移行の手間」と「期待できる効果」の2軸に置き、先に移すものを決めます。図6は8つの処理を配置した四象限図で、右ほど手間が大きく、上ほど効果が大きいことを表します。

左上の「最初に移す」領域に入るのは、通知メール、ポイント付与、出荷指示です。どれも決済が終わった後の処理で、少し遅れても注文の結果は変わらないため、キューに任せても利用者への影響が小さく済みます。右上の在庫更新は効果が大きい一方で、同じ在庫を二重に引き当てないための整合性の確保が要り、手間が大きくなります。そのため移行後も、注文APIが在庫サービスと決済ゲートウェイだけを同期で呼ぶ構成にします。

役割分担と引き継ぎ

移行は開発だけでは終わりません。開発、QA、プロダクト、運用の4つの役割が、工程を順に引き継ぎます。図7では役割ごとに横長の帯(レーン)を置き、各工程を、担当する役割の帯の中に描いています。矢印が帯をまたぐところが引き継ぎで、そこで責任が次の役割へ移ります。

開発が実装を終えると、QAが負荷試験を行います。基準に届かなければ、太い破線のとおり実装へ戻します。合格するとプロダクトが段階リリースへ進むかを判断し、運用がカナリア切替を行います。カナリア切替とは、利用者の一部の注文だけを新しい経路へ流して様子を見る方式です。問題がなければ、最後に全面切替へ進みます。

マイルストーン

時間の流れで見ると、移行は2026年11月2日の設計開始から、2027年3月12日の全面切替完了まで、約19週間です。図8の横軸は日数に比例しているので、点と点の間隔が、そのまま期間の長さを表します。

実装完了(12月25日)から負荷試験の開始(1月4日)までの10日間は、年末年始の休みを想定した例です。負荷試験は1月4日から22日までで、その合格が終わりの日付になります。合格は、本番の注文を新しい経路に触れさせてよいかを決める関門なので、太い輪で示しています。合格の3日後にカナリア5%が始まり、2週間後に50%へ広げます。5%と50%は、新しい経路へ流す注文の割合です。

作業の期間

ガントチャートは、作業(タスク)を期間の長さの棒にして、日付の軸へ並べた図です。図9の左端の列が5つのフェーズ(設計、実装、負荷試験、段階リリース、全面切替)、その右がフェーズに含まれる作業で、棒の左端が開始日、右端が終了日です。縦の細い線は月の区切りで、上の小さな目盛りは週の初め(月曜)を表します。

同じフェーズの中で棒が重なっているのは、作業を並行して進めるという意味です。設計では構成設計の終わり(11月13日)より前にイベント仕様の合意が始まり(11月9日)、実装では注文APIのキュー発行(注文確定のイベントをキューへ送る処理)の途中から出荷サービスの購読に着手します。フェーズの境目では棒が重ならず、前のフェーズが終わってから次が始まります。太い輪郭の棒(負荷試験)は、合格しないと次へ進めない関門です。日付は図8と同じです。

補足と限界

この文書は、移行の骨格をつかむために単純化しています。移行後に同期のまま残る処理と、非同期へ移る処理は次のとおりです。

処理移行後
在庫の引き当て同期のまま
決済の承認同期のまま
注文DBへの保存同期のまま
出荷の手配非同期(キューを購読)
通知メールの送信非同期(キューを購読)
  • 図4・図5・図6の数値と配置、図8・図9の日付は、すべて説明用の仮の値です。実際の値は、自分たちの計測と計画で決めてください
  • 同じイベントが2回届いたときに、結果が1回分と同じになるようにする工夫(冪等性)や、イベントの配信に失敗したときの再送は、この文書では扱っていません
  • 図1は注文APIからWebアプリへの応答の矢印を、図2は在庫サービス・注文DB・通知サービスを省いています。図は、読み取りやすさのために数を絞っています
