# ディープコードリーディング

ユーザーが指定したリポジトリや箇所を読み、主要な構成要素の役割と、処理がどこを通って動くかを理解できるように説明する。

## 調査

1. 対象のリポジトリ、ブランチまたはコミット、指定箇所を確認する。対象が特定できない場合だけ、必要な情報を尋ねる。
2. リポジトリの説明、構成、起動設定、入口となるコードを確認し、解説する範囲を決める。コードに関する主張は、文書だけで判断せず実装とも照合する。
3. リポジトリ全体の依頼では、主要な構成要素と依存関係を把握し、基本動作を示す代表的なフローを選ぶ。指定箇所の依頼では、その箇所の役割と周辺との接続を把握し、関係するフローをたどる。
4. 各フローについて、入口、主な呼び出し、データや状態の受け渡し、外部との接点、結果をコードで確認する。必要に応じて設定やテストも参照する。実行環境で変わる挙動は、確認できた条件を添える。

## 解説

- 最初に対象と全体像を短く述べる。次に構成要素の役割と関係、基本的な動作フローの順で説明する。指定箇所の場合も、全体の中での位置づけを示す。
- 読者が処理を追えるよう、フローを入口から結果まで順に説明する。重要な分岐や状態の変化は、その理解に必要な範囲で取り上げる。
- 主要な事実や処理の接続には、実際に確認したコードへのポインターを付ける。ファイルパスと行番号を基本とし、利用環境で行番号を取得できない場合はシンボル名など特定可能な位置を示す。リンクを使える環境では開ける形式にする。
- コードで確認できたことと推測を区別する。追跡できなかった接続や、実行しないと確定できない挙動は明示する。説明のために存在しない経路を補わない。
- 情報量は対象の広さに合わせる。広いリポジトリでは代表的なフローに絞り、対象外とした部分を明記する。ユーザーが深掘りしたい箇所を指定した場合は、そこを優先する。

調査のみの依頼ではコードを変更しない。欠陥の網羅的な指摘や改善案は、解説の目的に必要な場合か、ユーザーが求めた場合に扱う。
