GitHub・GiteaのIssue起票とプルリクエスト（PR）作成を、ユーザーが依頼した範囲で進めてください。自動呼出しは追加の操作への許可ではありません。すでに許可された操作について、同じ許可を再確認する必要はありません。

## 1. 依頼と作業先の規約を確認する

- Issue起票、PR作成、本文の準備のどれを求められているかを確認します。本文の準備だけなら、外部への作成は行いません。PR作成とマージは別の操作として扱います。
- 作業先で適用されるAGENTS.mdと、そこから参照する規約を読みます。このスキルは規約の代わりではありません。規約のパスや構成は導入先に合わせます。
- タイトル・本文の言語と形式、ブランチの命名、PRの取り込み先は、ユーザーの指定と導入先の規約に従います。指定がない取り込み先は、対象リポジトリの既定のブランチを確認して使います。
- PRでは現在のブランチとステージ済み・未ステージ・未追跡の変更を確認します。別の作業の変更を含めず、依頼された変更の差分と確認結果を把握します。

## 2. サービス・リポジトリ・認証を確認する

- Gitのリモートとユーザーが指定したURLから、サービス、接続先ホスト、所有者、リポジトリ名を特定します。複数の候補があって作成先を特定できない場合は、その点だけ確認します。Gitリポジトリ外からの依頼では、明示された作成先を使います。
- GitHubでは `gh`、Giteaでは `tea` を基本とし、対象に接続できる認証済み連携ツールやAPIも使えます。接続先ホスト、認証アカウント、読み書きの権限を確認します。CLIの初期設定だけを根拠に作成先を決めません。
- 使うサービスに対応する資料を読みます。GitHubでは [GitHubの操作例](references/github.md)、Giteaでは [Giteaの操作例](references/gitea.md)を参照します。他方の資料を毎回読む必要はありません。
- 認証情報は既存の認証設定から使い、コマンド引数・ログ・Issue本文・PR本文へ転記しません。リモートURLなどに秘密情報が含まれている場合は、その値を表示しません。
- 接続先や権限を確認できない場合は、認証やアクセス権の問題を伝えます。用意できるタイトル・本文は先に準備し、作成に必要な利用者の操作を説明します。接続先と権限を確認できるまで、外部への作成には進みません。

## 3. 重複を確認して内容を準備する

- 対象リポジトリの既存Issue・PRを検索し、同じ目的のものを確認します。PRでは変更元のブランチも照合します。同じ内容があれば、そのURLと状態を報告し、依頼に合うものか判断します。新規作成が不要なら重複して作成しません。既存本文の変更やコメント投稿は、依頼された場合に行います。
- Issueには目的・背景・完了条件をまとめます。不具合なら再現手順、期待する動作、実際の動作を含めます。PRには解決する問題、変更内容、確認結果、関連Issueをまとめます。リポジトリのテンプレートとユーザーの指定に合わせて調整します。
- 本文は実際の改行を維持します。CLIではUTF-8の一時ファイルから渡すなど、シェルの展開で本文が変わらない方法を使います。
- 内容や作成先に判断を左右する不足があれば、その点を確認します。作成を依頼されていて必要な情報が揃っている場合は、準備した内容で進めます。

## 4. 依頼された操作を実行する

- 本文の準備だけを依頼された場合は、タイトル・本文と想定する作成先を提示して終了します。
- Issueの起票では、対象リポジトリと準備したタイトル・本文を明示して作成します。
- PR作成では、依頼を実現するために必要なコミット・pushを導入先の規約に従って行い、push済みの変更元と確認済みの取り込み先を明示して作成します。フォークの場合は変更元の所有者も特定します。
- コマンドの引数はその環境のヘルプで、APIの項目は接続先の仕様で確認します。例のホスト名・所有者・ブランチ名をそのまま使いません。
- エラーやタイムアウトで作成されたか不明な場合は、一覧や本文・変更元を照合して作成済みか確認してから再試行します。確認できない場合は、不明な状態と失敗した操作を報告し、作成要求を繰り返しません。

## 5. 作成結果を確認して報告する

- 作成結果を再取得し、ホスト・リポジトリ、番号、URL、タイトル、本文を確認します。PRでは取り込み先と変更元も確認します。
- 確認できたIssue・PRのURL、変更内容や確認結果を報告します。失敗した操作や未検証の範囲があれば明記します。本文を準備しただけの状態を作成済みとは報告しません。
